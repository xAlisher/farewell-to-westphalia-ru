# Обработка issue по переводу

Конвейер отработан на #49 (терминология human governance, 2026-08-20). Держись его формы.

## Инварианты (нарушение = брак)

- **Правки текста — ТОЛЬКО в `work/ru-parts/<глава>/<chunk>.md`.** Всё остальное — производное:
  `ru-draft` ← assemble, `translations/ru` ← sync, `docs/` ← build_site. Никогда не редактируй
  производные напрямую — их перезапишет `propagate.py`.
- `docs/` — публичный сайт. Внутренние документы туда не кладут.
- Гейт после любой правки фрагмента: `python3 work/tools/gates.py check <глава> <ids>`.
- Ложные срабатывания гейта, признанные нормой: библиография гл. 19 (EN-цитаты ломают счётчик
  предложений), слияние предложений при char-ratio ≈ 1.0.

## Шаг 0 — Исследование претензии

1. `gh issue view <N>` — прочитай; в теле есть **Чанк:** `id` (точный адрес фрагмента) и страница.
2. **Проверь претензию против реальности языка** (WebSearch): корпуса/словари для коллизий,
   профильная литература для регистра, изданные переводы для прецедента (пример: Остром
   «Управляя общим» для governance-терминологии). Внутренняя логичность issue ≠ верность.
3. Вердикт: держит / не держит / держит с уточнением.

## Шаг 1 — Решение-док + ответ в issue

- `work/decisions/NNN-<slug>.md`: претензия, находки исследования **со ссылками на источники**,
  вердикт, принятые формулировки, что отклонено и почему, план реализации. Коммить.
- Комментарий в issue: вердикт + ссылка на док + источники. Отклонённое закрывай сразу
  (вежливо, с исследованием). Дубликаты закрывай ссылкой на решение-док.

## Шаг 2 — Полосы реализации

**Полоса 1 — точечная** (один фрагмент): правь чанк из issue → гейт → шаг 3.
Коммит в main напрямую: `fix: <суть> (closes #N)`.

**Полоса 2 — терминология** (термин по всей книге):
1. `work/glossary.json`: новая каноническая форма; старую — в `forbidden_variants`.
2. Охват: `grep -riE '<паттерн>' work/ru-parts/` — **обязательно case-insensitive** (в #49
   регистровое «Человеческое управление» ушло от lowercase-паттерна) и по обоим порядкам слов.
3. Параллельные агенты по одному на главу. В брифе агента:
   - ссылка на решение-док (читать первым);
   - правило полная/краткая форма; **какая форма санкционирована** — финальная проверка должна
     исключать её из «запрещённых» (whitelist), иначе агенты избегают нужной полной формы;
   - НЕ доверять предположению, где именно определение термина, — проверять по EN-чанкам;
   - падежи, не трогать ничего вне коллокации, сноски/markdown байт-в-байт;
   - вернуть по-файловый отчёт с каждым выбором.
4. Не забыть спутники: `work/summaries/` (рабочая память конвейера), README (таблица глав),
   заголовки глав (chunk NN-000).
5. Финальная проверка корпуса: case-insensitive grep, whitelist санкционированных форм, ноль прочих.
6. Гейты всех правленых фрагментов (`git diff --name-only` → по главам).
7. Ветка `fix/term-<slug>`, PR с «Closes #N», merge `gh pr merge --admin` (branch protection).

**Полоса 3 — спорное/смысловое**: метка, вопрос пользователю в чате, потом полоса 1/2.

## Шаг 3 — Распространение и проверка

```bash
python3 work/tools/propagate.py <глава> [...]   # assemble → translations/ru → build_site
```
Коммит/merge в main → workflow `build_site.yml` перегенерит docs/ → Pages.
**Проверь живой сайт** (curl нужной страницы на новую формулировку; помни: `grep -c` с нулём
совпадений даёт exit 1 — это успех для «старого термина нет»).

## Конкуренция

Точечные правки — в порядке поступления, конфликтовать не могут (разные чанки).
Терминологические — транзакция на всю книгу: не смешивать с точечными по тем же главам,
две терминологические — строго последовательно.
